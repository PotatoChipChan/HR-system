1. WHAT THE SYSTEM IS (context for a stranger)
================================================================================

SmartHR is a Flask + SQLite web HR system (Python, SQLite, plain HTML/CSS
templates with a custom design system - NOT Bootstrap at runtime). Demo app
database: instance/smarthr.db (created/seeded by running `python -X utf8
init_db.py`, which is idempotent).

Core entities:
  Company (1) -> Branch (3 real: 1=KL Headquarters, 2=Penang Office,
                 3=Johor Bahru Branch) -> Department (each belongs to exactly
                 one branch via branch_id) -> Employee (has branch_id AND
                 department_id, plus position_id -> Position catalog).

Position Catalog (already implemented, see plan_position_catalog.txt):
  - Table Position: per-department catalog of job titles.
      position_name TEXT NOT NULL CHECK(TRIM(position_name)=position_name
        AND position_name NOT LIKE '%  %' AND length(TRIM(position_name))>0),
      UNIQUE (department_id, position_name COLLATE NOCASE)   -- case-insensitive
    Names must be stored pre-trimmed with collapsed inner whitespace; the app
    normalizes with ' '.join(name.split()) before every insert.
  - Employee.position_id / Job_Posting.position_id / Vacancy_Request.position_id
    link rows; the legacy text columns (Employee.position, Job_Posting.title,
    Vacancy_Request.position_title) are kept as point-in-time display snapshots.
  - Identity/authorization: 6 fixed roles (Admin, HR, HR Manager, HR Director,
    Manager, Employee) enforced by @role_required decorators. Permissions are
    NOT in the DB.
  - Department manager: Department.department_manager_id -> Employee.
    Manager-role users who are NOT department managers are "branch-scoped":
    they see/act only inside session['branch_id'] (Sprint 10).
  - Login (app/auth/routes.py:118-121) sets session['is_dept_manager'] and
    session['managed_dept_id'] from Department.department_manager_id.

2. GOAL / REQUIREMENTS (project owner)
================================================================================

Requirement A - Branch Managers must be real, visible org units.
  - There must be a department named "Branch Manager" (in the Department
    table, one per branch) and, in the Position Catalog, a position named
    "(branch location) Branch Manager" - e.g. "Penang Branch Manager",
    "KL Branch Manager", "Johor Bahru Branch Manager" - so they appear in
    the Position Catalog and department lists.
  - Decision (owner): PER-BRANCH departments, i.e. each branch gets its own
    "Branch Manager" department containing exactly one branch-manager
    position. NOT a single shared department (a department can only belong
    to one branch; shared would be incoherent).

Requirement B - Top Management separates HQ managers from branch managers.
  - A "Top Management" department (KL Headquarters) must exist for HQ
    leadership; the CEO (Brian Harris) belongs there - he must NOT be a
    "KL Branch Manager".
  - C-suite positions: check existing employees for suitable people first;
    only if nobody exists, seed new demo employees. (Verified: apart from
    the CEO there are no C-suite staff - see section 5.2.)

Requirement C - Department form filters the manager dropdown by branch.
  - In "Add/Edit Department", when a branch is selected, the Department
    Manager dropdown must show ONLY managers of that branch (client-side
    filter, e.g. pick Penang Office -> only Penang managers). Server-side
    POST must also reject a manager from a different branch (anti-crafting).

Requirement D - Clean up demo/test artifacts.
  - Branch 4 "New Branch", departments 11 "New Department" and 12
    "New Department 2.0", their employees and positions are leftovers from
    earlier tests and must be deleted.

4. PROBLEM
================================================================================

1. Users cannot see or manage "who is the branch manager": no department,
   no position, no assignment UI - branch managers are invisible implicit
   role-scoping.
2. HQ leadership (CEO) has no home: making the KL branch manager the head
   of all KL managers conflates top management with branch management.
3. The Add/Edit Department form shows managers from ALL branches regardless
   of the chosen branch (confusing, error-prone), and its POST accepts
   cross-branch assignments.
4. Backfill re-runs promote custom-approved posting titles into the catalog
   (breaks the custom-review governance rule; 1 failing test).
5. Leftover demo artifacts ("New Branch" etc.) pollute branch/department
   lists and manager dropdowns.

5.3 Scoping exemption (keep Sprint 10 branch-wide behavior)

In app/auth/routes.py login (line 118-121), when looking up the employee's
managed department, ALSO fetch the department name. If the department_name is
exactly 'Branch Manager', set session['is_dept_manager'] = False (and
managed_dept_id = None). Rationale: the Branch Manager department's manager
IS the branch-wide manager; without this they would be restricted to only
that single department in vacancy request GET (recruitment/routes.py:1111)
and POST (line 1064). This keeps brian/weiliang/cheeseng/kevin_loh behaving
exactly as they do today (branch-wide). Top Management has no dept manager,
so brian remains a plain Manager - no session change needed for him.

5.4 Department form branch filter (requirement C)

  (a) _get_managers_for_company(): add e.branch_id to the SELECT
      (alias branch_id) so templates can tag options.
  (b) department_form.html:
        <option ... data-branch-id="{{ m.branch_id }}"> on every manager
        option; small <script> filterManagers():
          - on branch select change: hide options whose data-branch-id
            differs from the selected branch (mirror the filterPositions()
            pattern used in recruitment/add_posting.html);
          - on page load in EDIT mode: apply filter for
            department.branch_id immediately; the pre-selected manager
            option must stay visible even if filtered (edge case);
          - in ADD mode: show all until a branch is chosen.
        Dropdown label/hint may say managers shown depend on the branch.
      (c) Server-side guard in add_department POST + edit_department POST:
          if department_manager_id is submitted, look up the employee's
          branch_id and reject with a flash ("Manager ... does not belong to
          the selected branch.") if it differs from the submitted branch_id
          (add: branch_id must also resolve to an existing Branch, already
          partially done in add_department line 515).

5.5 Backfill governance fix (fixes the 59/60 suite)

In init_db.py backfill_position_links(): exclude Job_Posting titles that
originated from custom-approved vacancy requests from the source query, so a
re-run NEVER promotes custom titles. Implement via:
    LEFT JOIN Vacancy_Request vr ON vr.posting_id = Job_Posting.posting_id
    WHERE ... AND (vr.posting_id IS NULL OR vr.is_custom = 0)
(i.e. only backfill posting titles that were NOT created from a custom
request, or whose origin request is unknown). After this change
test_position_catalog.py must be 60/60.

7. RISKS / SIDE CASES
================================================================================

- Employee dept/position mismatch breaks backfill linking: always move the
  employee's department_id together with the position link (5.1).
- A manager assigned to BOTH a normal department and a Branch Manager
  department (rare): keep the existing single-row lookup semantics of
  auth/routes.py:118-121 (first match wins); document, do not over-engineer.
- Edit-mode filter edge: the currently assigned manager may come from the
  pre-selected branch only (server guard enforces it), but keep the option
  visible when the branch select is switched away.
- Duplicate "Branch Manager" department for a branch created twice: the seed
  is idempotent (exists-check by branch_id + department_name); a second
  department would also be allowed by the data model - rely on unique
  (branch_id, department_name)? Department has NO unique constraint today:
  the seed checks existence first; manual duplicates are the owner's choice.
- Backfill fix must not break the migration backfill for LEGACY postings:
  legacy postings have no origin vacancy request (vr.posting_id IS NULL) and
  are still backfilled.
- New seeded positions must satisfy the Position CHECK/unique constraints
  (normalize with ' '.join(name.split())).
- Deleting employees/positions for cleanup must respect FK order (5.6).
